已完整阅读 `index.html`、`app.js`、`content.js`、`styles.css`、`starfield.js`、根目录 `README.md`、`assets/README.md`；检查 Git 文件清单、部署标记、导航、路由、所有内容条目和组件间调用关系。

**总体判断：现有项目已经具备个人网站的基本栏目，但 Wiki 仍是项目条目的附属段落展示器。**主要缺口是作品与文档的入口组织、统一的数据读取、文档结构、异常状态，以及移动端与键盘操作。现有原生静态技术栈足以继续迭代，当前规模没有证据表明必须迁移 React、Vue 或引入构建工具。

### 3.3 信息架构问题

1. **“项目 Wiki”一级入口指向具体文章。**侧栏直接进入钻石大陆的翻译说明（`index.html:36`），没有“先选作品，再找文档”的索引层。
2. **项目归属表达不一致。**页面叫“参与项目”，但当前两条均来自 `projects`；真实的 `participations` 为空。更适合用“作品与项目”作总栏目，用类型标签表达个人作品或参与作品。
3. **主页没有突出当前作品。**“最近的项目”实际永远取数组第一项，当前为网站本身（`app.js:44`）。没有日期排序或精选字段，不能把它当作真实最近更新。
4. **网站建设说明占据多个主要入口。**侧栏底部、顶栏年份、页脚都通向部署说明。它适合作为维护文档，但不应压过作品介绍、玩法说明和用户需要查阅的 Wiki。
5. **身份与作品目录尚未形成闭环。**介绍中有 Minecraft 与 Blophy 身份，项目目录只有网站和钻石大陆。不能据此编造其他作品，应为用户后续补充真实作品留出结构。
6. **面包屑只有当前栏目文字。**没有“Wiki → 作品 → 当前文章”的层次，也不能逐级返回。

## 4. 组件结构与数据流

```text
content.js → window.SITE_CONTENT
                   ↓
app.js：locationState() → render() → #page-content.innerHTML
  ├─ renderHome / renderProfile / renderResources
  ├─ renderProjects / renderWiki / renderGallery / renderSearchPage
  ├─ 共用：sectionHeading / resourceCard / projectCard / emptyState
  ├─ 搜索：collectSearchItems → updateSearch / renderSearchPage
  └─ 交互：bindPageEvents、导航、群号复制、搜索快捷键

starfield.js → #starfield、#star-trail、#motion-toggle
styles.css → 所有静态外壳和模板输出
```

现有优点：展示与内容已分文件；资源卡片、项目卡片等存在函数级复用；文本大部分经过 `escapeHtml`；外链通常包含 `noreferrer` 或 `noopener noreferrer`；星空实现独立。

维护问题：

- 路由、渲染、查询、数据拼装、事件处理集中在一个闭包，缺少共享的“全部项目 / 默认文档 / 查找文章”函数。不同消费者出现数据范围不一致。
- 每次切页整块替换 `innerHTML`，无页面焦点交接；每次输入搜索重新生成全文索引。当前 27 条搜索记录规模很小，后者是增长风险，不应夸大为已测得性能故障。
- 首页数字、路由默认值、卡片入口、Wiki 解析分别决定项目与章节，容易漂移。
- 个人身份卡文案、部分标题、`LINKS / 10`、导航编号和年份存在模板内硬编码，README 所说的“只改 content.js”不能覆盖全部站点文字。
- `resourceCard(item, index)` 的 `index`、`projectCard(project, participation)` 的 `participation` 参数未使用。
- 当前内容为本地维护，未发现表单提交或远端用户输入进入内容对象；不应仅因使用 `innerHTML` 就宣布存在已证实的 XSS。将来支持外部内容时，应补充 URL 协议校验和富文本清洗。

这些是可直接从代码确认的值。实际整体观感、像素级排版与图片背景上的对比度，没有通过截图或视觉输入判断。

## 6. Wiki 结构与内容质量

```text
projects
├─ site-archive：个人档案站
│  ├─ overview：项目概览
│  ├─ structure：内容结构
│  ├─ maintenance：维护记录
│  └─ deploy：发布到 GitHub Pages
└─ diamond-continent-plus：钻石大陆加豪版
   ├─ translation-method：如何将整合包翻译为不同语言
   └─ workflow：流程梳理

participations：空数组
```

数据结构是 `project.pages[] → { id, title, section, body: string[] }`。正文每一条字符串都渲染为 `<p>`（`app.js:112`）。

- 翻译说明已有 8 段真实说明文字；文件路径、语言代码、步骤标题和脚本片段都混在普通段落中，没有标题层级、代码块、列表或可点击引用。
- “流程梳理”目前是 4 段介绍未来要写什么的说明，尚不是完整可执行的游玩流程；应标为整理中，不要把规划文字当成已完成攻略。
- `section` 实际为显示编号，不是分组层级；暂不支持多级目录、文章内目录、标题锚点或跨文档精确引用。
- 每篇文章下方的 `.article-pagination` 遍历所有章节，它是第二份目录，不是真正的上一篇 / 下一篇。
- 无文章独立摘要、适用版本、更新时间、草稿状态、作者/维护者、关联页面字段。项目年份不能替代文档更新时间。
- 所有项目卡片都进入 `/overview`，但钻石大陆没有这一章节。这一数据与路由约定冲突已经发生。
- 所有作品都被要求有 Wiki；尚不能清楚表达“展示作品，但不需要文档”的情况，与“部分作品 Wiki”的目标不完全吻合。

建议先支持可选 Wiki、明确默认文章、标题/段落/列表/代码/提示块等轻量结构。文章规模扩大后再评估 Markdown 和静态生成；不必立即引入新框架。

## 8. 动画与资源处理

### 8.1 动画

`starfield.js` 使用两层固定 Canvas：背景星点上限 260，拖尾上限 72，像素倍率上限 1.75；背景按约 30fps 节奏更新，拖尾跟随动画帧。

已有优化：检测减少动态偏好；页面后台暂停；触摸不产生拖尾；`pointer-events: none`；切页隐藏/恢复时清理与恢复；CSS 轨道与暂停类联动。

改进点：暂停偏好只保存在内存，刷新会重置；窗口尺寸变化立即重建星点，未合并连续 resize；减少动态规则把无限动画时长缩到 `.01ms`，并没有取消无限循环。当前初始暂停状态可阻止轨道运转，但在减少动态模式下手动再次开启时，CSS 与 Canvas 的行为应统一。没有进行实际帧率、耗电或设备性能测试。

## 11. Phase 2 建议实施范围

建议目标信息架构：

```text
首页：我是谁 + 精选作品 + Wiki 快速入口
关于我：个人介绍 + 创作身份 + 主页与社群
作品与项目：类型 / 状态 / 简介 / 真实作品入口 / 可选 Wiki
作品 Wiki：作品索引 → 文档分组 → 文章
资源：分类目录 + 精确搜索定位
图库：作品登记 + 署名与使用说明
```

按以下顺序实施，可以避免先改外观、再返工结构：

1. **统一数据与路由。**统一两个项目集合；区分作品展示与可选文档；显式默认文档；无效 Hash、未知项目、未知文章、空目录都有可恢复状态；保留现有有效链接。
2. **补作品与 Wiki 入口。**新增 Wiki 总目录；项目栏目命名与内容一致；首页使用明确精选而不是数组第一项；保留作者现有介绍与真实内容，不虚构作品。
3. **升级文档阅读结构。**正文支持标题、列表、代码和提示块；增加文章内目录、上一篇/下一篇、适用版本和更新时间等可选字段；未提供的信息保持未填写。
4. **完善交互。**移动菜单、键盘焦点、当前页语义、搜索精确定位、动态页面标题、资源筛选状态。
5. **整理 Design Token 与响应式。**统一字号、留白、容器和点击区域；将深/浅 Wiki 主题改为语义变量；保留已有星空品牌元素，不凭空判断素材风格。
6. **文本与 DOM 验收。**检查全部入口、空状态、旧链接及桌面/手机宽度；视觉验收和素材处理应作为明确分开的后续范围。

建议验收宽度：320、360、390、760、761、960、1100、1440px；另测横屏低高度与文字放大。它们是后续验证计划，不是已完成的浏览器测试。
